# Research: dynamic-providers

**Branch**: `007-dynamic-providers` | **Date**: 2026-11-04 | **Spec**: [spec.md](spec.md)

Every point the spec defers to planning is settled here. Each decision names the requirement it serves and the part of the codebase it touches. File references are to the code as merged on `main` (features 001 to 006).

## Findings that shape the design

- `src/surplus/evaluation.js` (`evaluateSurplus`) already takes a `services` array and reads only `id`, `name`, `quotas[]`, `resetCycleDays` and `surplus{weeklyQuotaId, sessionQuotaId, tool}` from it. The surplus logic is generic; what is fixed is the *source* of that array (`SERVICES`, imported in 14 places), the `SUPPORTED_SERVICE_IDS = ['claude','chatgpt']` allow-list used by validators, policy, ideas and runner config, and the display-order tie-break at `evaluation.js:328-331`.
- `src/data/rules.js` is the only code that is truly provider-specific: five hand-written rules naming `s.claude.weekly`, `s.chatgpt.codex_remaining`, `s.kilocode.credits` and so on. It must be replaced, not adapted.
- The shared store keeps ordinary records. `routing_config` records with namespaced logical keys already carry ideas, policy, runs and cycles with no backend change; `applySurplusRecords` silently ignores keys it does not know (`storage.js:263-275`), so new namespaces are safe on devices running the previous build.
- A backup is a copy of the whole SQLite file (`backup-service.js`), so every record type is restored together and consistently with no per-type code. FR-020 holds for shared mode by construction; only the local export needs a change.
- `applyQuotaRecord` stores any `{id}:{key}` it receives, and every consumer iterates the catalogue, never the state. Values written for unknown ids are therefore inert.
- `getResetInfo` already counts local calendar days from an injected `now`. `RecoBox` calls `getResetSignals(state, SERVICES)` without a `now`, so it falls back to `new Date()`; the surplus path injects one. FR-038 is met by passing a single `now` everywhere.

## Decisions

### D1. Identity scheme (FR-023)

- **Decision**: Provider id `p_` + 12 characters of base32 (`[a-z2-7]`) from `crypto.getRandomValues`; quota id `q_` + 8 characters of the same alphabet. Generated by an injected `newId` so tests are deterministic. Ids are immutable and never derived from a name.
- **Rationale**: The prefix makes the former fixed ids (`claude`, `chatgpt`, `copilot`, `openrouter`, `kilocode`, and quota ids such as `weekly`, `slot5h`) impossible to collide with and cheap to recognise as legacy. `isProviderId(id)` is a single regex, which lets validators accept new ids without a list. Neither id contains `:`, so `{providerId}:{quotaId}` quota keys and `{providerId}:{resetDate}` cycle keys keep parsing.
- **Alternatives**: UUID v4 (36 characters in every key, no benefit). Slug of the name (breaks on rename, collides with `claude`). Incrementing integer (collides across devices).

### D2. One runtime shape for the pure code (FR-011, FR-024)

- **Decision**: A pure `toRuntimeService(provider)` maps a stored provider to the shape the existing code reads: `{ id, name, color, cost, costCurrency, flags, note, resetType, resetCycleDays, quotas:[{id,label,type,currency,subnote,lowBalance,gates}], surplus }`. `resetCycleDays` is 7 for weekly, 30 for monthly (the cycle 003 already uses), the user's number for custom, `null` for none. `surplus` is present only when the profile is eligible (D9).
- **Rationale**: `evaluation.js`, `cycleReadings.js`, `cycles.js`, `instruction.js`, `getResetInfo`, `createWeeklySnapshot` and the runner keep their logic; they receive `services` built from the catalogue instead of `SERVICES`. The diff is concentrated in data sources and validators.
- **Alternatives**: Rewrite those modules around a new provider type (large diff, no behaviour gain, risks 006 regressions).

### D3. Where the catalogue lives (FR-019, FR-021, US4)

- **Decision**: One shared record per provider, `record_type = routing_config`, logical key `provider:{providerId}`; plus one `catalogue-order` record `{ids:[...]}`. Locally: `localStorage['kairos:providers']` = `{schemaVersion, providers:{[id]:payload}, order:[ids]}`. Deleting writes a **tombstone payload** (`status:'removed'`, captured name, `removedAt`) with an ordinary versioned `PUT`, never an HTTP delete.
- **Rationale**:
  - One record per provider gives per-provider optimistic concurrency, so two devices editing different providers never conflict, and editing the same one yields a 409 that is shown (US4-3).
  - A tombstone cannot be silently resurrected by a stale device (its `PUT` against an older version conflicts), keeps the captured name for every device's history (FR-028, FR-036), and is the "removed provider reference" entity.
  - A single `PUT` per edit is atomic from the server's view; locally a catalogue edit is one in-memory commit followed by one storage write (FR-021).
  - Reordering rewrites one small record, not N providers.
  - No schema or route change: same technique as 006.
- **Sync machinery**: the surplus engine (`src/surplus/engine.js`) already provides local-first writes, dirty tracking, debounced flush, 409 resolution, incremental pulls and full-pull delete detection. The plan **extracts that core into a generic record-sync module** (behaviour-preserving, protected by the existing `engine.test.js`/`store.test.js`) and instantiates it for the catalogue. A second hand-written engine is rejected as duplicated conflict logic.
- **Alternatives**: A single `providers` record holding the whole list (any edit on any device conflicts with any other; last writer silently drops the other's provider). A new `record_type` (needs a table rebuild with foreign keys; 006 already rejected it). Hard delete (loses the captured name and allows resurrection).

### D4. Quota readings stay where they are (FR-039, FR-022)

- **Decision**: Definitions (D3) hold no values. Values, reading stamps and the reset date keep the existing `quota_state` records and the `kairos-ai-quota-router:state` local key, now addressed by provider and quota ids (`{providerId}:{quotaId}`, `{providerId}:__ts_{quotaId}`, `{providerId}:__last_reset_date`). `buildDefaultState` returns `{}`; creating a provider writes its entered values and stamps in the same commit.
- **Legacy data**: entries under `claude`, `chatgpt`, etc. stay in the stored object, are never read (every consumer iterates the catalogue) and are written back unchanged, so they are neither imported nor deleted. `useSharedQuotaState` no longer seeds shared records from defaults; seeding is replaced by the writes made at provider creation.
- **Missing value**: a quota with no value yet (definition arrived before its readings on another device) is *unread*: the provider is excluded from recommendations for tasks that quota gates, with the reason "no reading yet for {quota}", and the card says so. This avoids inventing a number.
- **Alternatives**: Put the value in the definition (every reading becomes a conflicting catalogue write; breaks 003/005 stamp semantics). New storage key (would orphan or force a copy of legacy data, which FR-022 forbids).

### D5. Task-fit scale and how it combines with quota pressure (FR-012, FR-013)

- **Decision**: Fit levels `strong=3`, `acceptable=2`, `weak=1`, `none=0` (default for an undeclared task, shown as "Not set: treated as not suitable"). For a task `t` and provider `P`:
  1. *Gating pressure* `pressure(P,t)` = the highest consumed percentage among the quotas of `P` whose `gates` include `t` (`gates: null` means all tasks, the default). Percentages come from `getConsumedPct` (D6).
  2. *Blocked*: any gating quota is fully consumed (consumed 100, i.e. remaining 0 or balance ≤ 0). Blocked providers are excluded and listed with the reason. Quotas that do not gate `t` never block `t`.
  3. *Eligible*: fit ≥ 1, not blocked, every gating quota has a reading.
  4. *Band penalty*: pressure < 60 → 0; 60 ≤ pressure < 85 → 1; 85 ≤ pressure < 100 → 2.
  5. *Score* = fit − band penalty (range −1 to 3).
- **Rationale**: The legacy rules switch away from the preferred provider at 60 % and again at 85 % pressure (`rules.js:77,84`) and prefer a lighter-loaded provider of lower fit once the best one is loaded. A score of fit minus a band penalty expresses exactly that in one explicit formula: a strong-fit provider at 60–84 % (score 2) ties with an acceptable-fit provider at < 60 % (score 2), and the tie-break (D7) then prefers the lower pressure unless the reset favours the loaded one. The thresholds 60 and 85 are the legacy ones, so reference scenarios mostly agree.
- **Alternatives**: Weighted numeric score (opaque, harder to explain, breaks Constitution II/IV). Fit-first strictly (a strong-fit provider at 99 % would always beat an acceptable one at 5 %, which is the opposite of the product's purpose). User-editable thresholds (extra surface, not requested; can be added later behind `RULESET_VERSION`).

### D6. Currency balance to pressure (FR-013, FR-006)

- **Decision**: Each currency quota carries an optional `lowBalance` (a positive number in its own currency, default 5). Consumed percentage: balance ≤ 0 → 100; balance < 0.4 × lowBalance → 85; balance < lowBalance → 60; otherwise 20.
- **Rationale**: With the default 5 this reproduces the current table (`utils.js:9-16`: < 2 → 85, < 5 → 60, else 20) exactly, so existing weekly-history values (`consumedPct`) and card colours do not change, and the user gets a per-quota knob for currencies of different scale. Negative balances are refused at input (FR-006).
- **Alternatives**: Fixed thresholds per currency symbol (a table to maintain, wrong for the user's scale). Percentage of last top-up (needs a new field the user must keep updated).

### D7. One order-independent tie-break (FR-014, FR-034, US5-6)

- **Decision**: A single comparator `compareProviders(a, b, ctx)` in `src/providers/tiebreak.js`, a lexicographic key so the order is total and transitive, used by recommendations and by surplus selection. For recommendations the key is:
  1. score, descending (D5)
  2. pressure bucket `floor(pressure / 15)`, ascending
  3. days to reset, ascending, counting only providers with a reset in the future or today (`countdown` or `due`); `overdue`, `unset`, `invalid` and `none` sort after all known values
  4. pressure, ascending
  5. fit, descending
  6. name, compared after Unicode NFC normalisation, trimming and case folding
  7. provider id (always distinct, so the order is total)
  
  For surplus selection the key is: days to reset ascending (as today), then name, then id (criteria 6 and 7 are the shared order-independent tail).
- **Rationale**: Criterion 2 turns the legacy "within 15 points" band into fixed buckets, so "comparable pressure, sooner reset wins" (FR-015) is expressed without a pairwise threshold that is not transitive and would let sort order, and therefore creation order, leak into the outcome. Names are unique ignoring case (FR-002), so criterion 6 is already decisive in practice; the id guarantees totality. The explanation names the first criterion that separated the two best candidates (for instance "same score and pressure bucket; resets sooner (2d vs 5d)"; "tie broken by name").
- **Intended differences**: pressures 14 and 16 fall in different buckets where the legacy band treated them as comparable; surplus ties no longer follow display order. Both go into the before/after scenario list.
- **Alternatives**: Keep pairwise `|Δ| ≤ 15` (non-transitive). Tie-break by creation date (violates FR-014). Random (non-deterministic).

### D8. Generic rules, reset notes, reasons (FR-015, FR-016, FR-017)

- **Decision**: `recommend({ task, providers, state, now })` in `src/routing/engine.js` returns `{ rulesetVersion, taskId, primary, alternatives[], excluded[], reason, tieBreak }`, pure and deterministic, with no provider name or id anywhere in the module.
  - `primary` is the first eligible provider in D7 order; `alternatives` are the next eligible ones (at most 3), each with a one-line role (fit and pressure).
  - `excluded` lists every other provider with its cause: `not_suitable` (fit none or undeclared), `blocked` (names the exhausted quota), `unread` (names the quota).
  - `reason` is built from the same facts: fit, the gating quota and its pressure, days to reset, the criterion that decided against the runner-up, and the legacy reset note kept in generic form (due today; overdue; resets in ≤ 2 days, "spend it now").
  - With no eligible provider: `primary: null`, a reason that says whether there is no provider, none suited, or all blocked, and, when reset dates are known, the soonest reset among blocked providers (edge cases).
- **Dropped legacy behaviour** (documented intended differences): `daily_chat` redirecting away from a provider that resets within 2 days "to preserve the refresh for work tasks", the `oneshot` USD > 1 cut-off, and free-text advice such as "copilot for IDE completion in parallel". They encode named-provider judgement that user-declared fit and gating now express.

### D9. Surplus profile and eligibility (FR-031, FR-032)

- **Decision**: `provider.surplus = { tool, weeklyQuotaId, sessionQuotaId } | null`, where `tool ∈ SUPPORTED_TOOLS = ['claude','codex']` (new constant replacing `SUPPORTED_SERVICE_IDS`; it lists tools the runner has adapters for, not providers). `surplusProblems(provider)` returns the unmet conditions as user-facing strings: no supported tool; schedule is not weekly; weekly quota not designated or not a percentage quota; session window not designated or not a percentage quota; the two designations are the same quota. `toRuntimeService` exposes `surplus` only when the list is empty, so `evaluateSurplus` sees exactly what it saw before. A provider with problems never appears in settings, notices or suggestions, and its form shows the list (US5-5).
- **Inactive, not erased**: when conditions stop holding (edge case), the per-provider settings stay in the policy but the provider drops out of the evaluated set, with the reason shown in its form.
- **Alternatives**: Infer the tool from the name (hard-codes names). Let any percentage quota act as weekly (breaks the weekly calibrations of 006).

### D10. Per-provider surplus settings (FR-033)

- **Decision**: Policy schema v2 renames the per-service map to `providers`, keyed by provider id, created on first use with the existing defaults (all off, disclosures unacknowledged). Global fields (`protectedHours`, `costPct`, `thresholds`, `projectsBaseFolder`) are kept as they are. A stored v1 policy is read as: global fields carried over, its `services` object moved verbatim into an inert `legacy` field that no code reads or validates, so former per-service settings are neither applied nor lost (FR-022). Deleting a provider prunes its entry. A duplicate gets no entry (defaults, off).
- **Alternatives**: Keep the key name `services` (validator then cannot tell legacy ids from new ones without a list). Drop v1 settings (violates the "not modified" wording of FR-022).

### D11. Records, ideas and history that name a provider (FR-036, US5-9)

- **Decision**: Persisted field names stay (`serviceId` on ideas, runs and cycles), so stored records need no migration; the value is now a provider id or, for old records, a legacy id. Validators accept `isProviderId(id) || LEGACY_SERVICE_IDS.includes(id)`; only the runner/engine *write* new ids. New optional field `providerName` is captured on run records at claim time and on cycle records when written (a run keeps the name it had when it started). Display resolves in this order: live provider name; captured `providerName`; tombstone name; static legacy name table (`legacyProviders.js`, display only) for the five old ids; otherwise the id marked "removed". Anything resolved from a tombstone, a captured name or the legacy table is labelled "removed".
- **Alternatives**: Rename the field to `providerId` everywhere (touches every stored record and the runner contract for no behaviour gain). Rewrite old records (forbidden by FR-022).

### D12. Weekly history (FR-026 to FR-030, SC-010)

- **Decision**: Snapshots gain an additive `providers` map `{ [providerId]: { providerId, name, captured{color,note,flags}, lastResetDate, removedAt?, quotas:{ [quotaId]: {quotaId,label,type,value,currency,consumedPct,subnote} } } }`; `schemaVersion: 2` on new writes. A v1 snapshot is already a valid v2 snapshot with no `providers`; its `services` map is the legacy section and is carried verbatim into any v2 snapshot written for the same week (one snapshot per workspace and week is preserved). Rules:
  - `createWeeklySnapshot` takes the week's existing snapshot: entries of providers no longer live are kept and marked `removedAt`; live providers' entries are rebuilt (so values and, in the current week only, the name follow edits). **Completed weeks are never rewritten.**
  - With zero providers nothing new is recorded (FR-026).
  - Series are derived by provider id; `deriveServiceHistorySeries` becomes `deriveProviderHistorySeries` and also accepts legacy ids from the `services` section. A week before the provider existed yields `missing_service` ("no history recorded", never zero).
  - Snapshots from another device mentioning an unknown provider are shown from their own data and create nothing (FR-030); `applySnapshotRecord` already never touches live state.
  - **Cross-device merge**: a week's snapshot syncs as one record, and today's `upsertCurrentWeekSnapshot`/`applySnapshotRecord` replace the whole week. With providers that would let a stale or v1 remote snapshot drop local entries, including those of removed providers. A pure `mergeWeekSnapshots(local, remote)` replaces replacement for any week both sides hold: union on provider id; an entry carrying `removedAt` wins over one without, otherwise the later `capturedAt`; the legacy `services` section is kept verbatim from whichever side has it.
- **Interpretation recorded**: FR-027 ("a snapshot already recorded MUST NOT be rewritten by a rename") is read as applying to completed weeks. The in-progress week is updated in place by design since feature 005 (`recordWeeklySnapshot`), and display always uses the provider's current name for live providers, so the observable series is unchanged.

### D13. Runner: catalogue read, authorisation, allowance (FR-035, SC-011)

- **Decision**:
  1. The runner builds `services` on every tick from the `provider:*` records in its pull (`derive()` in `loop.js:281`), replacing the `SERVICES` default. Tombstones and invalid records are ignored.
  2. Authorisation never derives from the store. `config.json` schema v2 replaces `allowServices` with `allowProviders: [{ providerId, tool, name, allowedAt }]`, written only by a local CLI command. The guard in `guardService` becomes: policy `autoRunEnabled` and disclosures (as today) **and** `allowProviders` contains the id **and the catalogue's current `tool` equals the pinned `tool`** (else `tool_changed`) **and** the idea's local approval (unchanged) **and** global switch, lease, STOP file (unchanged).
  3. A legacy `allowServices` in an existing file is preserved verbatim under `legacyAllowServices` and ignored.
  4. CLI: `runner allow <name-or-id>` lists catalogue providers eligible for surplus, shows name and tool, and records the pin after an explicit confirmation; `runner disallow <name-or-id>`; `status` shows allowed providers and flags allowed ids missing from the catalogue.
- **Rationale**: A provider written straight into the store has an unknown id, so it is not allowed; an existing allowed provider whose tool is switched in the store fails the pin; `autoRunEnabled` in the shared policy is necessary but never sufficient, exactly as in 006 FR-012 to FR-014. No new network or file surface is added.
- **Alternatives**: Trust the catalogue's tool (a store write could redirect an allowed id to a different CLI). Allow by name (names change and are not unique across time).

### D14. Deleting or changing a provider with a run in progress (FR-037, US5-8)

- **Decision**: The browser detects an active run from run records with `status: 'running'` for that provider id. The confirmation dialog warns first. After confirmation the browser writes the change (tombstone, `surplusEnabled=false`, `autoRunEnabled=false`, or a new tool). The runner's existing 5-second stop watcher is extended to also re-derive, after its incremental pull, whether the active run's provider is still runnable (active, surplus on, automatic runs on, tool equal to the pin). If not, it stops through the same path as a global stop (partial output kept, idea back to retriable, run record finalised with `stopped_by_user` and the provider name captured at start).
- **Alternatives**: Have the browser also write the global stop (would halt every other provider's runs for one provider's edit). Wait for the run to finish (violates FR-037).

### D15. Conflict, atomicity, validation (FR-003, FR-006, FR-007, FR-021)

- **Decision**: Pure reducers in `src/providers/catalogue.js` (`addProvider`, `updateProvider`, `removeProvider`, `duplicateProvider`, `reorderProviders`) take `{catalogue, state, now, newId}` and return `{ok:true, catalogue, state, effects}` or `{ok:false, errors:[{path,message}]}`; nothing is committed on refusal or cancel. Validation: name 1 to 60 characters after trimming, unique under the D7 name normalisation; 1 to 8 quotas; label 1 to 40; percentages 0 to 100; currency balance ≥ 0 with a symbol of 1 to 3 characters and `lowBalance` > 0; schedule `custom` needs an integer 1 to 366; cost ≥ 0 with currency; flags ≤ 8 of ≤ 30 characters; note ≤ 500; colour `#rrggbb` or null. Changing a quota's type is refused by the reducer unless the patch carries a new value for it (FR-007); the form asks for it. Removing the last quota is refused. Changing the schedule while a reset date is recorded returns a `needsConfirmation` effect (confirm or edit the date); an inconsistent date is flagged by `getResetInfo` as today.
- **Server conflicts**: a 409 on a provider record is resolved like the surplus engine: refetch, show "changed on another device" with the other device's version, let the user reapply. A tombstone always wins over an edit.

### D16. Local export and backup (FR-020, US4-4/5)

- **Decision**: Backup/restore needs no code: the SQLite copy carries every record. `exportLocalStateForMigration` iterates the catalogue instead of `SERVICES` and additionally emits the `provider:*` and `catalogue-order` records (as `routing_config`), so the export carries definitions, readings and weekly history as the spec states, and not surplus records (unchanged scope).

### D17. Day basis (FR-038)

- **Decision**: One `now` per render pass is created at the top of `App` (and injected into `recommend`, `getResetSignals`, `evaluateSurplus`), replacing implicit `new Date()` calls in `RecoBox` and `SummaryBar`. A scenario test runs the three at 23:59 and 00:01 local time with `TZ` set.

### D18. No provider named in code (FR-011, SC-005)

- **Decision**: A guard test scans `src/providers`, `src/routing`, `src/surplus`, `runner` (excluding tests, fixtures and `legacyProviders.js`) for the former ids and names and fails if found. The former five providers and the legacy rules move to `src/routing/fixtures/` (test-only) for the before/after harness.

### D19. Constitution amendment (Product Constraints)

- **Decision**: Version 1.0.0 → **1.1.0** (MINOR: materially expanded mandate). Replace the first Product Constraint with: "The canonical product scope is quota-aware routing across the AI providers the user declares (subscriptions with percentage quotas and pay-as-you-go balances); the application MUST NOT ship a fixed provider list." Replace the second with: "Supported quota input modes MUST remain explicit (`consumed_pct`, `remaining_pct`, `currency`) and be declared per quota of each provider." Update the Sync Impact Report and `Last Amended`. Proposed via the feature's pull request per the Governance section.

### D21. Surplus rule-set version and duplicate names after sync

- **Surplus `RULESET_VERSION` 1 → 2** (Constitution II, traceability). The selection order and explanation of `evaluateSurplus` change (FR-034), and `Run.decisionInputs` records the version, so two runs with different selection rules must not share a number. The rules R1 to R7 keep their meaning. `ROUTING_RULESET_VERSION` (routing recommendations) and `RULESET_VERSION` (surplus evaluation) version different rule sets; a comment next to each says so.
- **Duplicate names across devices** (FR-002). Uniqueness is enforced by the reducers on one device only, so two devices working offline can each create "X". `nameConflicts(catalogue)` lists the later-created duplicates (earlier `createdAt` wins, then the smaller id). Both providers stay in the catalogue and in recommendations (ordered by the tie-break, so the outcome is still deterministic), the UI shows "name used twice: rename" and opens the form on the name field, and nothing is renamed or deleted automatically.
- **Unread quotas** (D4) are handled everywhere a value is read, not only in routing: card ("No reading yet"), pressure helpers (ignored, never NaN), summary, snapshots (skipped until the first reading) and surplus (already treats a non-number as unknown).

### D22. Two behaviours the spec does not list (convergence review, T125)

Reviewed after implementation; both are kept, for the reasons below.

- **"Reset" became "Clear readings"** (`SummaryBar`, `resetAll` in both quota hooks). The former button restored the default values of the five fixed services. With no shipped providers there are no defaults (FR-001), so restoring them is impossible. Clearing every reading of the declared providers is the closest meaning: values and stamps become `null` (unread), reset dates are cleared, providers and history are untouched, and shared mode writes the same `null` values so other devices converge. Entries of former ids in the stored state are left alone (FR-022). Reverting to the old wording would promise a behaviour that no longer exists; the label and tooltip now say what happens.
- **First-contact adoption of local readings** (`useSharedQuotaState`, effect keyed on `bootstrapped`). When a workspace is joined, readings of declared providers that exist only locally (entered offline, or before a workspace was set) are written once to the store. Without it a provider created offline would keep its definition (synced by the catalogue engine, FR-019) but lose its readings on the next device, leaving it unread everywhere. It only writes keys that have no record in the store and only for declared providers, so it can neither overwrite another device's reading nor export legacy data (FR-022), and it mirrors what the surplus engine already does for ideas created before a workspace existed.
- No spec or contract text changes; if either behaviour is unwanted it can be removed without touching the data model.

### D20. Scale and performance (FR-009, SC-009)

- **Decision**: Recommendation is O(providers × quotas) per task and runs synchronously on selection; surplus evaluation is O(providers × ideas). With 20 providers of up to 8 quotas this is a few hundred operations, so no memoisation or pagination is planned. A unit test with 20 providers asserts completion under a loose bound and, more importantly, identical output for shuffled input. The weekly-history panel already renders one series per selected provider.

## Open risks

- **R1**: Extracting the generic sync core from the surplus engine touches working 006 code. Mitigation: do it as a standalone behaviour-preserving step, first in the task order, with the existing engine tests unchanged.
- **R2**: Reading a v1 policy or snapshot must never lose data. Mitigation: tests that feed fixtures captured from the current build (legacy policy, snapshot, runs, cycles, runner config) and assert byte-equivalence of the legacy sections after a v2 write.
- **R3**: UI surface is the largest piece of work (provider form with quotas, fits, surplus profile, delete dialog, empty state). Mitigation: keep it plain CSS Modules like the rest; the form is driven by the pure reducers so it holds no rules.
